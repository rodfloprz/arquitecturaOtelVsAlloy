title: Discovery service: un concepto, seis problemas distintos
---
<p class="lead">No existe un único «discovery service» en ninguno de los dos proyectos. Lo que cada uno llama discovery resuelve problemas distintos, y la pregunta útil es cuál de ellos necesita resolver cada capa de la arquitectura.</p>

### Los seis conceptos que no deben mezclarse

| Concepto | Qué decide | Dónde ocurre en Alloy | Dónde ocurre en Contrib |
| --- | --- | --- | --- |
| Service discovery | Qué cargas de trabajo existen | Componentes `discovery.*` (kubernetes, ec2, azure, dns, file, http, consul, docker, kubelet, process, relabel y más) {{V}} | Service discovery de Prometheus dentro del receiver `prometheus`; receivers con observers {{I}} |
| Scrape target discovery | Qué endpoints `/metrics` se raspan | `discovery.*` más `prometheus.operator.servicemonitors`, `.podmonitors`, `.probes` y `.scrapeconfigs` {{V}} | Receiver `prometheus` con la configuración `scrape_config` completa de Prometheus; Target Allocator para ServiceMonitor y PodMonitor {{V}} |
| Collector discovery | Qué instancias de gateway reciben datos | Resolvers de `otelcol.exporter.loadbalancing`: static, dns, kubernetes, aws_cloud_map {{V}} | Resolvers del exportador `load_balancing`: static, dns, k8s, aws_cloud_map {{V}} |
| Endpoint discovery | Qué direcciones usar para exportar | Mismos resolvers; `discovery.dns` para otros usos | Mismos resolvers; `dns` resuelve un Service headless |
| Collector clustering | Cómo se coordinan las instancias | Bloque `clustering`: gossip, consistencia eventual, activación por componente {{V}} | No hay clustering nativo; el reparto lo hace el Target Allocator o el balanceador {{V}} |
| Asignación y balanceo de targets | Qué instancia raspa qué target | Hashing consistente local entre pares del clúster {{V}} | Target Allocator con estrategias de asignación; el exportador `load_balancing` usa hashing consistente para datos, no para targets {{V}} |

### Matriz de capacidades

| Capacidad | Alloy | OpenTelemetry Collector Contrib |
| --- | --- | --- |
| Descubrir pods y servicios de Kubernetes | Nativa: `discovery.kubernetes`, `discovery.kubelet` {{V}} | Nativa en el receiver Prometheus (kubernetes_sd); con Target Allocator para reparto {{V}} |
| Descubrir VMs en AWS y Azure | Nativa: `discovery.ec2`, `discovery.azure`, `discovery.lightsail` {{V}} | Nativa vía ec2_sd y azure_sd del receiver Prometheus {{I}}; sin reparto automático fuera de Kubernetes |
| Descubrir Prometheus exporters | Nativa: `discovery.*` más `prometheus.scrape`; exporters embebidos `prometheus.exporter.*` {{V}} | Nativa con el receiver `prometheus`; los exporters son procesos aparte |
| Descubrir endpoints de aplicaciones | `discovery.*` y `prometheus.operator.*` {{V}} | Receiver Prometheus; observers con receiver_creator {{I}} |
| Descubrir gateways OTel | Resolvers de `otelcol.exporter.loadbalancing` {{V}} | Resolvers de `load_balancing`; el resolver `k8s` exige RBAC sobre EndpointSlice {{V}} |
| Clustering de collectors | Nativa, explícita por componente {{V}} | No existe; requiere Target Allocator (solo Kubernetes) {{V}} |
| Asignación de targets | Hashing consistente; etiquetas de targets deben ser idénticas entre nodos {{V}} | Target Allocator del OTel Operator {{V}} |
| Reglas ServiceMonitor y PodMonitor | `prometheus.operator.servicemonitors` y `.podmonitors` {{V}} | Target Allocator {{V}} |

Cinco de ocho capacidades son nativas en Alloy sin componente externo; en Contrib, tres son nativas y las restantes dependen del Operator, el Target Allocator o la configuración de Prometheus.
